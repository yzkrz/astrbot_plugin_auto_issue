# astrbot_plugin_auto_issue

在用户交流群中收集需求 / Bug 反馈，由 AI 多轮追问补全细节，整理成规范的 GitHub Issue，经确认后自动发布到指定仓库。

## 使用方式

```
用户：@机器人 /issue
机器人：📝 已进入 issue 生成模式，接下来的文字和图片都会被记录。…
用户：导出的 Excel 打开是乱码
用户：[截图]
群友B：我也遇到了，WPS 打开是正常的
用户：生成
机器人：收到，正在整理…
机器人：截图里看到版本是 v2.3.1。请问你是在 Windows 还是 macOS 上用 Excel 打开的？
群友B：我这边是 Windows 11
用户：我也是 Windows，Excel 2019
用户：继续
机器人：📝 Issue 草稿预览
       标题：[Bug] 导出的 CSV 在 Windows Excel 中打开出现中文乱码
       标签：bug
       ...
       ⏳ 等待管理员审核，审核通过后才会发布。
管理员：确认
机器人：Issue 已发布：https://github.com/owner/repo/issues/123
```

### 指令

| 指令 | 说明 |
| --- | --- |
| `/issue` | 进入生成模式：先收集多条消息，发送「生成」后 AI 开始整理并追问。包含多个独立问题时会自动拆分为多个 issue |
| `/issue list` | 列出仓库当前所有 open 的 issue（不含 PR） |
| `/issue test` | 检查自己的 Token：账号、Token 类型与权限、仓库角色，能否创建 issue / 评论 / 打标签，以及图床是否可写 |
| `/issue <编号>` | 查看 issue 详情及最近 3 条评论 |
| `/issue <编号> <内容>` | 为 issue 添加评论（可附带图片） |
| `/issue ban @用户 clear` | 清空该用户的违规次数，不影响封禁状态（仅 AstrBot 管理员） |
| `/issue ban @用户 <时长>` | 禁止该用户使用 issue 功能，`0` 为解封（违规次数保留）。时长支持中文和英文单位，可组合，见下方示例；也可写 `/issue ban <用户ID> <分钟>`（仅 AstrBot 管理员） |
| `/issue ban` | 查看当前封禁列表和违规记录（仅 AstrBot 管理员） |

`/反馈` 是 `/issue` 的别名。群聊中需要 @机器人，私聊无需 @。

### 生成模式

生成模式分为以下几个阶段：

1. **收集阶段**：发送 `/issue` 后，群里的文字和图片会被逐条记录，机器人不回复，也不调用 AI。可以分多条慢慢描述。
2. **整理阶段**：发起人（或管理员、用户白名单中的用户）发送「生成」后，AI 先识别所有图片，再通读全部记录，信息不足就追问，充足就给出草稿。
3. **回答与修改**：AI 提问或给出草稿后，群友可以分多条回答、补充或提修改意见，这些消息先积累起来；发起人（或管理员、用户白名单中的用户）发送「继续」后，才把这一批消息一起交给 AI。

- 「生成」只在收集阶段有效，用来开始整理；整理阶段不能用它跳过追问。追问达到「最大追问轮数」后，AI 会根据已有信息直接出草稿。
- 图片既会作为插图附在 issue 末尾，也会先交给模型识别，提取报错、日志、版本号等信息写进正文。识别结果会被缓存，每张图只识别一次。
- 会话期间整个群共享同一个会话，群内其他人的补充也会被采纳并记录为参与者。
- 一次反馈多个问题时，AI 会拆分为多个草稿，每个草稿只附带与之相关的图片。
- 收集阶段记录的全部内容如果都与项目无关，AI 会拒绝并清空记录，回到收集阶段重新描述。
- 与项目开发无关的内容（八卦、娱乐、时事、广告、其他产品的问题等）会被拒绝生成 issue；群友之间的闲聊会被静默忽略。被拒绝或忽略的消息不会写进 issue，发送者也不会被记为参与者。判断是否相关时以配置中的「项目背景介绍」为准，建议认真填写。
- 预览阶段回复修改意见（例如「把第 2 个和第 3 个合并」）后发送「继续」，AI 会修改草稿后再次预览。
- 一批消息全部是闲聊或与项目无关时，AI 会忽略或拒绝，这批消息整体撤销，不写进 issue，发送者也不会记为参与者。
- AI 调用失败时这批消息会保留，再发一次「继续」即可重试。
- **管理员审核**（「发布前需要管理员审核」，默认开启）：草稿预览后，只有 AstrBot 管理员或配置的「审核员」回复「确认」才会发布，「关联」「评论」同样需要审核。其他人（包括发起人）只能回复修改意见并由发起人发送「继续」重新生成；发起人仍可「放弃」草稿或「取消」整个会话。等待审核期间会话超时时间延长为「等待审核的超时时间」（默认 30 分钟）。
- 回复「确认」发布全部草稿，「确认 1 3」只发布指定编号，剩余草稿可继续修改或发布。
- **检查已有 issue**：每次出草稿后，AI 会比对仓库中已有的 issue（默认只比对 open 的、最近更新的 100 条），在预览中列出可能重复或相关的 issue，包括编号、状态、作者、创建时间、评论数、标签、链接、摘要和判断理由。之后可以选择：

  | 回复 | 效果 |
  | --- | --- |
  | `确认` | 仍然新建 issue |
  | `关联 [草稿编号] #12` | 新建 issue，并在正文「相关 issue」中提及 #12（GitHub 会在 #12 下显示引用），可写多个 `#12 #15` |
  | `评论 [草稿编号] #12` | 不新建，把草稿内容作为补充反馈评论到 #12 下 |
  | `放弃 [草稿编号]` | 不发送该草稿，可写多个编号 |

  只有一个草稿时可省略草稿编号。`关联`、`评论` 也可以指定 AI 没有列出的 issue。
- 「生成」「继续」「放弃」「取消」可由发起人、用户白名单中的用户或 AstrBot 管理员操作；开启审核时「确认」「关联」「评论」只能由管理员或审核员操作。
- 会话期间仍可 @机器人 使用 `/issue list`、`/issue <编号>` 等查询指令。
- 超过设置的超时时间无人发言，会话自动结束。
- **引用预览重启**：每条草稿预览末尾带有一行 `预览编号：IS-XXXXXXXX`。会话超时（或 AstrBot 重启）后，管理员或审核员在原群**引用这条预览消息**并发送「重启」，即可恢复这些草稿继续审核、修改或发布。
  - 只认机器人自己发出的、带预览编号的消息：平台提供被引用消息的发送者时会核对是否为机器人，引用别人的消息不会触发。
  - 只有本群当前没有进行中（包括刚刚发起、正在启动）的 issue 会话时才能重启；同一时刻一个群只会有一个会话。只能在原群重启。
  - 草稿全部发布、放弃、被取消，或发起人被封禁后，预览编号失效。
  - 过期草稿默认保留 7 天（「过期草稿保留天数」），期间对应的图片副本也会保留。

`/issue` 后面跟其他无法识别的内容时，会回复用法说明。

## 封禁

### 时长写法

`/issue ban` 的时长支持多种写法，可以组合：

| 写法 | 含义 |
| --- | --- |
| `30`、`30m`、`30 分钟`、`30min` | 30 分钟（纯数字按分钟） |
| `2h`、`2小时`、`2个小时`、`两个钟头` | 2 小时 |
| `3d`、`3天`、`3日` | 3 天 |
| `1周`、`1星期`、`1礼拜`、`1w` | 1 周 |
| `1个月`、`1month` | 1 个月（30 天） |
| `1年`、`1y`、`1year` | 1 年（365 天） |
| `30s`、`30秒` | 30 秒（不足 1 分钟按 1 分钟处理） |
| `1h30m`、`1天6小时`、`1个半小时` | 组合时长，相加 |
| `半小时`、`俩小时`、`仨小时`、`两个半小时` | 支持 半 / 俩 / 仨 |
| `一小时`、`十五分钟`、`两个小时`、`一百二十分钟`、`二十三分钟` | 支持中文数字（一/壹、两/贰、十/拾、百、千、万） |
| `三个 小时`、`3 个 小时`、`1个月零3天` | 量词「个」和连接词「零」可有可无，空格也不影响 |
| `三万五千分钟`、`一亿年`、`一千万亿年` | 支持 万 / 亿 / 兆 等大数，按实际时长显示（如「禁止 1 亿年」） |
| `1.5d`、`1.5天`、`0.5h` | 支持小数 |

单位可用中文（分、分钟、时、小时、钟头、日、天、周、星期、礼拜、月、年）或英文缩写（m/min、h/hr、d、w、mo、y 等），单位前的「个」字可省略。

- 只有 AstrBot 管理员可以封禁 / 解封，管理员本身不受封禁影响，也不能封禁自己。
- 封禁时，该用户发起的所有进行中的 issue 收集会话（包括其他群里的）会立即结束，草稿不会发布。
- 封禁期间该用户不能发起 issue、查询、评论或测试权限；在进行中的会话里，他发送的消息会被直接忽略，不会写进 issue，也不会记为参与者。
- 封禁记录保存在插件数据目录的 `bans.json` 中，重启后仍然有效，到期自动解封。
- 封禁对所有群生效。

## 违禁词

配置中的「违禁词」（默认为空，在配置页自行添加）是硬性规则，**只在本地用正则匹配，不经过 AI 判断，也不会发给任何模型**：

- 群友在 issue 会话中发的消息、以及 `/issue` 指令本身只要包含任意违禁词，就在收到时直接拒绝、不记录，并按违规计次警告（与下方的违规处罚共用次数）。这些消息不会进入任何模型。
- 图片识别结果在交给整理和审核模型**之前**先做违禁词检查，命中的图片被屏蔽，发送者记一次违规。
- AI 的回复（追问、拒绝说明、草稿）中出现违禁词，视为被注入人格：本次回复作废，记发起人一次违规（见下方「人格注入检测」）。
- 不泄露违禁词：警告和提示只说「包含违禁词」，不说是哪个词；机器人发出的其他文字中若出现违禁词，统一替换为 `***`，不透露长度；违禁词清单不会写进任何提示词。
- 不区分大小写和全半角，字符之间夹杂空格或符号也能识别（如 `g a y`、`猫*娘`）。英文违禁词前面紧挨字母时不算（如 `regay`）。
- 管理员发送含违禁词的消息时只拒绝记录，不处罚。
- @ 某人时对方昵称中的违禁词不会连累发送者。

## 人格注入检测

群友可能会诱导 AI 换一种人格说话（例如让它自称猫娘、句尾加「喵」）。开启「检查 AI 回复是否被注入人格」（默认开启）后，AI 每次追问或给出草稿，都会先检查再发出：

1. 先在本地检查回复中是否有违禁词（包括没按格式输出的原文），命中则直接判定为被注入，不再调用模型。违禁词检查不受这个开关影响，始终开启。
2. 再交给「审核模型」判断语气是否偏离设定：角色扮演、卖萌撒娇、口癖、颜文字、称呼「主人」、调情、八卦、夹带给其他 AI 的指令等。正常引用的界面文字、报错和用户原话不算。拿不准时不判定为注入。

判定为被注入时：

- 本次 AI 回复作废，不发到群里；诱导 AI 的这一批消息被撤销，不会写进 issue。已有的草稿保留。
- 记**发起人**一次违规，按下方的违规处罚计次（与同一批的其他违规合并，只计一次）；累计到第 3 次时封禁，会话随之结束。发起人是管理员时只作废不处罚。
- **不透露原因**：群里只会看到警告或封禁通知本身（如「【警告】你发布的内容违反群规。」），不会提到 AI、输出检测或命中的内容。真实原因只写入 AstrBot 日志，管理员可在日志中查看。管理员作为发起人时只提示「本次未生成回复」。
- 审核模型返回格式异常时，本次回复同样作废，提示重试，不计违规。

每轮会多一次模型调用（使用「审核模型」）。

## 违规检测与自动处罚

每次发送「生成」/「继续」时，插件会用「审核模型」检测这一批新的群聊消息（包括图片识别结果），找出违规内容。**不只是发起人，会话期间群里任何人发的都会被检测。**

- 算违规：嘲笑或调侃他人性取向、性别、地域等，低俗色情，针对他人的脏话和人身攻击，泄露隐私，广告，诱导机器人生成上述内容等。
- 不算违规：正常的反馈和讨论、普通闲聊、不针对任何人的口头禅和吐槽。
- 违规消息会从记录中移除，不会写进 issue；违规图片不会附进 issue；只发过违规内容的人不会记为参与者。其余消息照常整理，信息足够就照常出草稿，不够就按原来的方式追问或拒绝。

处罚按每人的累计违规次数计算（同一批消息中多次违规只计一次）：

| 次数 | 处罚 |
| --- | --- |
| 第 1 次 | 警告 |
| 第 2 次 | 严重警告 |
| 第 3 次起 | 禁止使用 issue 功能，依次为 5 分钟、15 分钟、1 小时、6 小时、12 小时、1 天、3 天、7 天，之后每次 7 天 |

- 警告会 @ 违规者发到群里。被封禁时，他发起的 issue 收集会话立即结束。
- AstrBot 管理员不会被检测和处罚。
- 违规次数保存在插件数据目录的 `strikes.json` 中，不会自动清零。管理员可以用 `/issue ban` 查看；`/issue ban @用户 0` 只解封、不清零，`/issue ban @用户 clear` 只清零、不解封。
- 检测失败时不影响 issue 整理，只是这一批不做处罚。

## 内容安全

为防止群友借插件往仓库里发恶搞、侮辱或违规内容（例如「在页面上增加 xx 是 gay 的闪烁标语」），插件有三层防护：

1. **整理提示词中的安全规则**：放在提示词最后、优先级最高。针对个人或群体的侮辱、调侃、造谣，在界面 / 文案 / 文档 / 彩蛋中植入点名或恶搞内容，泄露隐私，广告，恶意功能等，即使包装成正常的需求或 Bug，也一律拒绝。
2. **防注入**：群聊内容、昵称、图片识别结果都以 JSON 字符串交给 AI，并明确告知这些只是数据。「忽略之前的规则」「开发者模式」「这是测试」之类的话无效，也无法伪造助手发言。AI 输出格式异常时不会把原文发到群里。
3. **发布前独立审核**（「发布前独立审核草稿」，默认开启）：每次出草稿后，再用一次独立的 AI 调用逐个审核。审核看不到群聊记录，只看草稿本身，所以群聊里的诱导话术影响不到它。未通过的草稿直接移除，正常的草稿保留；审核结果异常时整批作废，宁可不发。

可以在「补充拒绝规则」中按行添加项目自己的规则，会同时加入整理和审核的提示词。

## Token 说明

- **classic token**：勾选 `repo` 权限即可访问私有仓库（创建 issue、评论、查询）。只勾 `public_repo` 时访问私有仓库会返回「未找到」，插件会提示缺少 repo 权限。
- **Fine-grained token**：授予目标仓库 Issues: Read and write 权限。注意 Fine-grained token 无法访问**他人个人账号下**的仓库，所以仓库协作者必须使用 classic token。
- 每个用户的 Token 只决定 issue / 评论的创建者；图片统一用「图床 Token」（留空则为默认 Token）上传到图床仓库，协作者的 Token 不需要图床仓库的权限。

## PicX 图床

1. 用 [PicX](https://picx.xpoet.cn) 一键配置会在你的账号下创建图床仓库（默认 `picx-ih`，分支 `master`）。
2. 在插件配置中填写「PicX 图床仓库」，如 `yourname/picx-ih`。
3. 选择链接规则：
   - 图床仓库**公开**：可用 jsDelivr / Statically / ChinaJsDelivr 等 CDN，国内访问更快。
   - 图床仓库**私有**：只能用 GitHub 规则，且只有对图床仓库有权限的人才能看到图片。
4. 图片按上传月份分文件夹，以内容的 SHA-256 命名，路径形如 `auto-issue/202610/<64 位哈希>.png`，同一个月内相同图片只上传一次；与 PicX 管理的其他图片互不影响，也可以在 PicX 中浏览和管理。
5. 图片在**发布 issue 时**才上传，只上传草稿中实际用到的图片；上传失败会退回使用聊天平台原始链接。

## 注意

- 默认配置下，会话进行期间该群的**所有消息**都会被插件接管（全部先记录，交给 AI 时再判断是否相关），不会触发机器人的普通聊天回复。收集阶段不做相关性过滤，闲聊过的群友也会出现在参与者名单里。如果群比较活跃，建议开启「会话中仅处理 @机器人 的消息」。
- 未配置图床时，图片直接引用聊天平台的 URL，QQ 等平台的图片链接可能在一段时间后失效。
